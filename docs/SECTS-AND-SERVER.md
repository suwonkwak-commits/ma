# 문파 재건·표국 운영·서버 확장 설계

이 문서는 향후 구현할 게임 구조의 설계안이다. 현재 게임에는 수련·전투·환생이 구현되어 있고, 이번 이야기 추가는 세계관과 서막을 읽는 기능이다. 아래의 문파 영입·인력·파견·표국·서버는 아직 구현되지 않았다. 세력과 지역은 사용자가 제시한 노선을 기준으로 삼고, 동선 조정 제안과 세부 기능·보상 수치는 설계 초안으로 구분한다.

사용자는 후속 선택에서 **NPC 문파 운영에 집중**하는 방향을 확정했다. 여기서 문파는 실제 플레이어들의 길드가 아니라 개인 캠페인에서 해방하고 운영하는 NPC 세력이다. 서버 규모는 개인 진행과 문파 경제를 많은 이용자에게 안정적으로 제공하기 위한 계획으로 잡는다.

## 플레이어가 쌓는 두 종류의 성장

주인공의 경지는 한 생의 성장이고, 해방한 강호는 여러 생에 걸쳐 남는 성장이다. 처음에는 자신의 한 끼와 약값을 버는 협객이지만, 나중에는 여러 문파와 표국을 이끄는 재건맹의 맹주가 된다. 전투를 반복할수록 살아난 문파의 사람·생산·전승이 늘어나야 한다.

| 영역 | 의미 | 기록의 주체 |
| --- | --- | --- |
| NPC 문파와 가문 | 개인 캠페인에서 구원하고 동맹을 맺는 세력 | 플레이어 개인 |
| 재건맹 | 주인공이 이끄는 NPC 세력들의 연맹 | 플레이어 개인 |
| 표국과 파견대 | 영입한 인재를 편성해 자원을 얻는 운영 기반 | 플레이어 개인 |

한 계정의 문파 해방·인재·표국은 그 플레이어의 개인 진행이다. 다른 이용자가 내 이야기의 장문인을 소유하거나 내 문파를 초기화할 수 없다. 이번 계획에는 유저 길드 가입·채팅·협동 토벌을 필수 개발 단계로 넣지 않는다.

## 반복 플레이의 흐름

1. **침식의 근원을 찾는다.** 문파의 강탈·실종·약재 유통 같은 사건을 조사하고 마교가 차지한 길목을 제압한다.
2. **수뇌부를 제압하고 사술을 끊는다.** 장문인·가주와의 대결은 원한을 해소하는 장면이면서, 마교가 걸어 놓은 제어를 부수는 전투다.
3. **사람을 구하고 문파를 재건한다.** 부상자 치료, 납치된 제자 구출, 빼앗긴 비급 회수처럼 문파마다 다른 재건 과제를 수행한다.
4. **자발적인 동맹을 맺는다.** 해방된 문파는 정체성과 전통을 지키며 재건맹에 합류한다. 플레이어가 그들의 새 지배자가 되는 대신, 약속을 지켜 지휘를 맡는다.
5. **인재를 편성해 표국과 거점에 보낸다.** 문파의 강점을 살린 호송·정찰·약재 회수 임무로 금자와 재료를 얻는다.
6. **전승과 운영을 키운다.** 무공·의복·영약·시설이 성장하고, 더 깊이 침식된 다음 문파에 도전한다.

한 문파의 해방은 고유한 전승과 인재를 얻는 영구 성취다. 반복 전투와 파견에서는 성장 재료를 얻는다. 같은 장문인을 매번 처음 구출한 것으로 처리하거나, 같은 고유 인재를 무한 복제하지 않는다.

## 사용자 지정 노선과 단계별 역할

이야기용 작업 노선은 **모용 → 개방 기능 개방 → 하북팽 → 진주언 → 소림 기능 개방 → 화산·종남 전쟁 → 무당 → 남궁 → 강서 → 하오문 분타 기능 개방 → 광주 → 광서 → 사천 → 운남 점창 → 곤륜 → 천산 마교**로 구성한다. 청죽무관은 주인공의 출신·초기 수련 배경으로 남기고, 첫 해방 세력은 모용세가로 둔다.

사용자는 ‘호북팽’을 **무당파로 수정**한다고 명시적으로 확인했다. 남방의 광주→광서 순서는 이동 방향을 다듬기 위한 제안으로, 원래 제시된 광서→광주 순서에 대한 최종 확정과는 구분한다. 하오문은 고정된 본산보다 여러 지역의 분타로 연결되는 정보망으로 배치한다.

아래는 이 게임의 창작 세계에서 적용할 배치와 기능이다. 모든 무협 작품에 공통된 지리·문파 설정이나 역사적 사실로 표현하지 않는다. 기존 네 전투 지역 ID가 이미 이 캠페인 노선으로 교체된 것도 아니다.

강한 세력이 초반에 등장한다고 해당 문파 전체의 무공 수준을 낮추지는 않는다. 초반 해방은 고립된 거점·통제 장치·마교의 보급을 공략하고, 사술로 제 실력을 쓰지 못하는 인재와 협력하는 사건으로 설계한다. 전투 경지는 개별 전투의 난도이고, 해방 순서는 침식 구조와 이야기의 순서다. 두 값을 같은 서열로 취급하지 않는다.

## 세 가지 기능 개방을 구분하는 법

개방·소림·하오문은 단순히 부하 수를 늘리는 단계가 아니라 운영의 선택지를 바꾸는 관문으로 둔다. 아래는 후속 구현안이며 현재 실제로 열린 기능은 아니다.

| 관문 | 주 기능 | 화면에서 알게 되는 것 | 경계 |
| --- | --- | --- | --- |
| 개방 | 공개 정찰·자원 정보·지도와 표행로 | 일반 사건의 위치, 어떤 길에서 무엇을 얻는지, 새 호송로의 조건 | 비밀 의뢰와 희귀 NPC 교역 기능은 하오문과 구분한다. |
| 소림 | 사술 정화·인재 치료·고급 수련 | 오염과 부상을 회복하는 방법, 수련의 추가 선택지 | 기존 **화경부터 환생** 규칙을 바꾸거나 소림 해방을 환생의 추가 필수 조건으로 넣지 않는다. |
| 하오문 | 은밀한 정보·희귀 NPC 교역·숨은 의뢰 | 마교 내부의 비밀, 잠입·회수 의뢰, 제한된 NPC 물품 | 다른 유저와의 거래소가 아니다. 공개 지도 정보는 개방의 역할로 남긴다. |

희귀 교역의 재고·가격·구매 제한은 서버가 관리하는 NPC 상점 규칙으로 정의한다. 숨은 의뢰의 추가 위험과 보상도 시작 전에 확인할 수 있게 한다. 핵심 해방이나 대표 무공을 사후 결제 조건으로 바꾸지 않는다.

## 화산·종남 전쟁은 개인 캠페인 사건이다

마교가 조작한 명령·증거·보급 문제가 두 문파의 전쟁을 부추긴다는 사건으로 구성한다. 플레이어는 지원 순서, 구출할 인재, 확보할 증거와 공동 작전의 역할을 선택한다. 선택은 대사·지원 효과·인재와의 관계에 반영하되, 주요 해방 전승을 영구적으로 놓치는지 여부는 선택 전에 분명히 보여 줘야 한다.

이 사건은 NPC 세력 사이의 전쟁이다. 다른 이용자와 싸우는 PvP나 유저 길드전, 실시간 매칭 서버를 요구하지 않는다. 플레이어의 문파 진행과 분리된 가상의 전황·지원 상태를 계정별로 저장한다. 두 문파를 모두 재건맹의 공동 작전에 참여시키는 흐름을 기본 안으로 둔다.

## 문파 ID·지역 ID·서사 단계 ID

위 표의 카드 ID는 **서사 노선 단계**를 가리킨다. `jiangxi-region`, `guangxi-region`, `guangzhou-region`을 문파 소유권 ID로 사용하지 않는다. `hwasan-jongnam`이나 `sichuan-sects`처럼 여러 대상을 포함한 단계도 개별 문파의 해방 상태를 하나로 덮어쓰지 않는다.

후속 서버 모델은 `CampaignStage`가 `Region`과 여러 `Faction`을 참조하도록 한다. 예를 들어 사천 단계는 사천 권역과 아미·당문·청성의 개별 세력 ID를 참조하고, 각 세력의 재건·동맹·영구 보상을 따로 기록한다. 현재 이야기 카드에서 `regionId: null`인 것은 실제 전투 지역과 연결하지 않은 초안이라는 뜻이다.

기본 무공은 문파마다 전투 방식이 달라지는 보상이어야 한다. 새로운 세력을 구했는데 같은 공격력 숫자만 받는 구조보다, 검법·보법·심법·기타 무공의 운용 역할과 전투 표현이 달라지는 방향이 좋다.

## 인력은 수량과 얼굴을 함께 가진다

명명된 핵심 인재와 일반 제자를 함께 운영한다. 장문인·가주는 문파의 전승과 재건을 담당하고, 표행 경험이 있는 제자는 표사로 일한다. 모든 이름 있는 고수를 같은 채집 인력으로 취급하지 않는다.

초기 인재 정보는 **등급·특기 태그·상태** 정도로 시작한다. 특기는 호위·정찰·의술·수로처럼 임무와 바로 연결한다. 세부 성격·피로·관계 수치를 처음부터 많이 늘려 매 접속마다 인력 정리를 해야 하는 흐름은 만들지 않는다.

| 상태 | 할 수 있는 일 |
| --- | --- |
| 대기 | 임무 또는 지원 편성에 참여 |
| 파견 중 | 현재 임무 전담. 다른 파견에 중복 편성 불가 |
| 휴식 중 | 정해진 시간 뒤 자동으로 대기 복귀 |
| 부상 | 표시된 회복 조건을 충족한 뒤 대기 복귀 |

플레이어 주인공은 기본 전투를 계속하며, 파견은 NPC 인재가 맡는다. 추후 전투 지원 NPC를 넣으면 같은 인재를 전투 지원과 파견에 동시에 배치하지 못하게 한다. 편성 저장과 일괄 재파견으로 반복 조작을 줄인다.

## 표행과 파견

초기에는 짧은 육로 호송, 약재 수송, 산길 정찰의 세 유형으로 검증한다. 긴 임무는 수로·원정으로 넓힌다. 예시 시간은 체험용 5~15분, 일상용 1시간, 장기용 4~8시간이며 실제 플레이에 맞춰 조정한다.

임무 화면은 시작하기 전에 다음 정보를 보여 준다.

- 필요한 인원과 추천 특기, 예상 소요 시간
- 기본 지급 금자·재료와 추가 획득 가능 보상
- 성공률·부상 가능성이 있다면 실제 적용 확률과 실패 시 기본 지급 범위
- 파견 중 해당 인재를 다른 곳에 쓸 수 없다는 상태

초기 핵심 임무는 확정 기본 보상을 제공하고 특기 적합도에 따른 추가 보상을 둔다. 실패로 모든 진척을 잃거나 인재가 영구 소멸하는 규칙은 초기 파견에 넣지 않는다. 물자 공급이 있어야 재건이 계속된다는 서사와 보상 감각을 함께 유지한다.

표행은 정해진 한 번의 임무다. 로그아웃한 일수만큼 같은 임무가 자동으로 무한 반복된 것으로 계산하지 않는다. 기존 자동 수련의 최대 8시간 보상과 별도로, 서버가 각 임무의 시작·완료 시각을 관리하고 완료한 한 번의 결과만 지급한다.

## 환생과 문파의 관계

아래는 문파·파견을 구현할 때 적용할 확장 규칙이다. 현재 게임이 이미 문파를 보존하거나 파견 보상을 계산하고 있다는 뜻은 아니다.

| 범위 | 환생 시 제안 |
| --- | --- |
| 현재 생의 경지·내공·금자·무공 수련도·공적 | 기존 환생 규칙에 따라 초기화·환산 |
| 해방한 문파·재건 과제 완료·동맹·영입 인재·표국 시설 | 보존 |
| 해금한 비급의 목록과 제작법 | 보존하되, 이번 생의 무공 숙련은 다시 수련 |
| 의상·검기·시설 외형 등 소유 상품 | 보존 |
| 약재·광석 등 추가 성장 재료 | 환산 대상·잔여량 규칙을 자원별로 명시한 뒤 구현 |
| 영약 등 소모품 | 보유·소비·환생 정책을 상품 도입 전에 결정하고 구매 화면에도 표시 |

주인공의 내공이 비워져도 구해 낸 문파의 자유와 약속은 남는다. 따라서 환생 때 같은 사람을 다시 세뇌된 상태로 돌리거나, 이미 얻은 유료 외형을 지우지 않는다. 재건 기반이 남아 다음 생의 성장이 더 매끄럽다는 보상을 만든다.

환생과 파견 보상을 함께 넣을 때는 시점 규칙도 필요하다. 환생 확정 시 이미 완료된 미수령 임무를 먼저 정산하고 그 생의 환산을 한 번 수행한다. 진행 중인 임무는 유지하며 완료 후 새 생의 획득량으로 기록하는 안을 기본으로 검증한다. 한 임무의 보상을 이전 생과 다음 생 양쪽에 넣지 않는다. 임무·생 회차·지급 기록으로 이를 확인할 수 있어야 한다.

## 수익화가 이야기 보상을 살리는 방식

해방 직후의 보상은 플레이어가 해당 문파를 구한 이유와 연결한다. 핵심 비급, 기본 도복, 첫 동맹 인재는 캠페인 보상으로 제공한다. 추가 외형과 편의는 그 보상의 활용을 넓힌다.

| 제공 경로 | 상품·보상 예시 |
| --- | --- |
| 이야기 보상 | 문파의 대표 무공 해금, 기본 도복, 동맹 인재, 영약 처방 |
| 반복 플레이 | 비급 성장 재료, 약재, 광석, 제작용 영약 재료 |
| 천옥·유료 상품 후보 | 문파 예복과 문양, 특별한 검기 연출, 표국 간판·수레·수련장 외형 |
| 편의 후보 | 편성 저장 칸, 제한된 임무 예약 등. 무료 기본 범위와 상한을 먼저 확정 |
| 영약 상품 후보 | 게임 안에서 얻을 수 있는 보조 영약의 확정 구성. 효과·개수·기간·환생 보존 여부를 먼저 공개 |

대표 무공의 첫 획득이나 문파 해방 자체를 결제해야 마무리할 수 있게 하면, 구원의 성취와 보상의 연결이 약해진다. 첫 출시에서는 해방의 성취를 먼저 완성한 뒤 외형과 제한된 편의를 판매하는 방향으로 검증한다. 현재 실제 결제·상점은 없다. 천옥의 현재 규칙과 이후 결제 원장 분리는 [경제 설계](ECONOMY.md)를 따른다.

## 서버의 첫 형태

큰 이용자 수를 받을 수 있는 기반은 **계정 인증 + 서버 데이터베이스 + 기능별 모듈로 나눈 하나의 백엔드**부터 준비한다. 개인 캠페인·문파 재건·인재·파견·재화의 경계를 코드와 데이터에서 분리하면, 이후 필요한 부분을 별도 프로세스로 옮길 수 있다. 현재는 배포 제공자나 규모·요금제를 확정하지 않는다.

| 데이터 영역 | 주요 책임 |
| --- | --- |
| 계정·플레이어 | 인증, 저장 버전, 마지막 서버 정산 시점 |
| 개인 캠페인·NPC 세력 | 해방·재건·동맹 단계, 영구 보상 수령 이력 |
| 인재·시설 | 인재의 고유 ID, 특기, 상태, 현재 배치, 시설 단계 |
| 파견 | 임무 ID, 적용 규칙 버전, 편성, 시작·완료 시각, 결과·수령 상태 |
| 재화 원장 | 금자·획득 천옥·유료 천옥의 증감 사유, 원본 거래·보상 ID |
| 계정 저장 복원 | 기기 간 진행 복원, 동시 접속 충돌 처리, 서버 정산 결과 동기화 |

파견 시작은 서버 트랜잭션으로 인재의 대기 상태를 확인하고 인원 잠금과 임무 생성을 함께 확정한다. 완료·수령도 임무 ID를 기준으로 한 번만 처리하며, 같은 수령 요청을 재전송하면 이전 결과를 돌려준다. 결과 지급과 지갑 반영이 서로 다른 성공 상태로 남지 않도록 한다.

서버 시간을 기준으로 완료 여부를 판단한다. 클라이언트가 보낸 시각·보상액·인재 상태를 그대로 믿지 않는다. 긴급 밸런스 조정이 있어도 이미 출발한 임무의 보상이 예고 없이 달라지지 않도록 출발 시 적용 버전과 조건을 저장한다.

실제 결제를 도입할 때는 돈으로 산 천옥을 스토어 거래 검증 뒤 서버 원장에 기록한다. 로컬 잔액을 유료 결제의 증거로 사용하지 않는다. 환불·구매 복원·재시도도 같은 원본 거래 ID로 연결한다.

모든 자동 전투를 화면의 2초 공격마다 서버가 방송할 필요는 없다. 클라이언트는 연출을 재생하고, 서버는 검증 가능한 시작 상태·경과 시간·전투 규칙으로 정산하는 방식을 우선 검토한다. 파견도 접속 중인 유저 수에 비례해 매초 검사하기보다 완료 시각을 인덱스로 조회하거나 지연 작업으로 처리한다.

## 이용자 수가 늘 때의 확장 순서

1. 계정 저장·파견·재화 지급의 정확성과 장애 복구를 먼저 검증한다.
2. API 프로세스를 상태 없이 늘릴 수 있게 하고, 작업 큐로 완료 처리·보상 알림을 분리한다.
3. 실제 느린 쿼리를 기준으로 데이터베이스 인덱스와 읽기 캐시를 보강한다.
4. 파견 정산·아이템 제작·알림처럼 별도 부하가 확인된 기능을 전용 작업자로 분리한다.
5. 부하 시험에서 동시 접속·임무 완료·보상 수령이 몰릴 때의 지연과 실패율을 확인하고 운영 규모를 정한다.

처음부터 많은 마이크로서비스나 복잡한 컨테이너 클러스터를 운영하는 대신, 위의 데이터 경계와 지급 규칙을 지키면서 실제 부하에 맞춰 확장한다.

## 단계별 개발 완료 기준

| 단계 | 이번에 검증할 경험 | 완료를 판단할 증거 |
| --- | --- | --- |
| 이야기와 첫 문파 | 서막 → 사건 조사 → 첫 수뇌부 제압 → 재건 → 동맹의 감정적 연결 | 테스트 유저가 주인공의 목표와 문파가 합류하는 이유를 설명할 수 있음 |
| 개인 문파·표국 | 첫 인재 영입, 한 임무 편성, 오프라인 완료, 한 번의 보상 수령 | 중복 편성·중복 지급·시각 변경·환생 경계 테스트와 서버 저장 복원 |
| 계정·기기 간 복원 | 같은 개인 문파를 다른 기기에서도 이어서 운영 | 오래된 기기의 덮어쓰기 방지, 중복 접속 중 보상 원장 일치, 계정 복구 |
| 규모 확장 | 접속·파견 완료·수령 집중과 장애 복구 | 목표 부하에서의 측정값, 실패 후 재시도와 원장 일치 |

초기 지표는 첫 문파 해방까지 걸린 시간, 첫 인재 파견률, 첫 임무 수령률, 동맹 후 재방문, 파견 보상 사용처, 환생 후 재성장 속도를 본다. 먼저 첫 문파 한 곳에서 재미를 확인한 뒤 문파 수와 서버 규모를 늘린다.
